# Отчёт по Спринту 4: Переход к распределённой сети нод и старт Web UI

## 1. Цель спринта

Перевести проект `blockchain_logistics` от локального однопользовательского блокчейн-скрипта к распределённой P2P-системе из нескольких независимых нод, способных обмениваться информацией о состоянии цепочки и блоками по сети (без использования Docker), а также заложить основу веб-интерфейса для демонстрации на следующем этапе.

---

## 2. Итоги спринта: что реализовано

### Выполнение требований спринта
* [x] **Независимый запуск нескольких нод:** реализован CLI-запуск (`run_node.py`) и конфигурация `NodeSettings`; каждая нода работает как самостоятельный процесс на собственном порту с изолированным JSON-хранилищем.
* [x] **Общая история и совместимость сети:** внедрён детерминированный генезис-блок (`GENESIS_TIMESTAMP = "2026-01-01T00:00:00+00:00"`) и проверка совпадения `genesis_hash` при подключении пиров.
* [x] **Установление взаимодействия по адресам:** реализована регистрация пиров (`POST /api/v1/peers/register`) с проверкой доступности и поддержкой двустороннего рукопожатия (`bidirectional`).
* [x] **Получение информации о другой ноде:** реализован опрос состояния соседа (`GET /api/v1/peers/inspect` → `GET /api/v1/node/info`) с расчётом разницы высоты цепочки и совместимости генезиса.
* [x] **Обмен блоками в двух режимах (Push и Pull):**
  * **Push:** отправка блока пиру или всем пирам (`POST /api/v1/blocks/{index}/broadcast` → `POST /api/v1/blocks/receive`).
  * **Pull:** запрос конкретного или следующего ожидаемого блока у соседа (`POST /api/v1/blocks/fetch` → `GET /api/v1/blocks/{index}`).
* [x] **Многоступенчатая валидация внешних блоков:** каждый входящий блок проверяется по 5 критериям (отсутствие дубликата, последовательность `index`, совпадение `prev_hash`, валидность хеша каждой транзакции, валидность хеша блока).
* [x] **Отклонение некорректных блоков с диагностикой:** при любой ошибке блок не записывается в цепочку, а клиент получает структурированный ответ с HTTP-статусом, машиночитаемым `error_code` и пояснением.
* [x] **Старт Web UI:** создан встроенный веб-интерфейс (`app/static/index.html`), доступный на корневом маршруте `/` каждой ноды.
* [x] **Подготовлены обязательные артефакты и тесты:** архитектура, контракты API, сценарии тестирования, инструкция по запуску и автоматические тесты.

### Ключевые технические доработки ядра (исправления после Спринта 3)
* Исправлена десериализация `Transaction.from_dict()` и `Block.from_dict()`: сохранённые хеши больше не пересчитываются молча при загрузке, что позволяет выявлять подмену полей в JSON.
* Уточнён порядок проверок в `Blockchain.validate_chain()` и добавлены методы `validate_incoming_block()` и `receive_block()`.
* Добавлена потокобезопасная блокировка (`threading.RLock`) и атомарная запись JSON-хранилища через временный файл (`*.tmp` + `os.replace`).

## 3. Распределение ролей и вклад каждого участника (команда из 5 человек)

В рамках спринта работа была распределена между 5 ключевыми ролями с привлечением ИИ-ассистента в роли инженера-консультанта по сетевой интеграции.

### 1. Архитектор (Участник 1)
* **Зона ответственности:** проектирование сетевого взаимодействия, выбор стека и обеспечение архитектурной целостности распределённой системы.
* **Что сделал:**
  * Совместно с ИИ-консультантом выбрал и обосновал протокол взаимодействия **HTTP/REST + JSON** (FastAPI + `httpx`) как оптимальный вариант без Docker, совместимый со структурой проекта и браузерным UI.
  * Спроектировал равноправную P2P-топологию независимых нод с изолированными хранилищами и общей историей через детерминированный генезис-блок.
  * Определил архитектуру двух сценариев обмена блоками (**Push** и **Pull**), потокобезопасность операций над цепочкой (`RLock`) и атомарную запись файлов на диск.
  * Проконтролировал разделение ответственности по слоям (`blockchain` → `services` → `schemas` → `api/v1/endpoints`).
* **Артефакты:** `docs/network-architecture.md`, схема взаимодействия нод.

### 2. Аналитик (Участник 2)
* **Зона ответственности:** формализация требований взаимодействия, проектирование API-контрактов и справочника ошибок.
* **Что сделал:**
  * Перевёл цели спринта в конкретные функциональные требования для межсервисного взаимодействия нод.
  * Описал полную спецификацию REST API (13 эндпоинтов: управление нодой, пирами, валидацией и блоками), форматы запросов и ответов.
  * Разработал единый формат ошибок и классификатор кодов отказа (`INVALID_TRANSACTION_HASH`, `INVALID_BLOCK_HASH`, `PREV_HASH_MISMATCH`, `INVALID_BLOCK_INDEX`, `DUPLICATE_BLOCK`, `GENESIS_MISMATCH`, `PEER_UNREACHABLE`, `INVALID_BLOCK_FORMAT`, `REMOTE_BLOCK_NOT_FOUND`).
  * Согласовал единый формат транзакций и блоков между нодами и документацией, а также подготовил руководство по запуску и итоговый отчёт спринта.
* **Артефакты:** `docs/network-requirements.md`, `docs/run-guide.md`, `docs/sprint4-report.md`.

### 3. Backend-разработчик (Участник 3)
* **Зона ответственности:** доработка ядра блокчейна, реализация сетевого слоя, REST API и CLI-запуска нод.
* **Что сделал:**
  * Исправил баги Спринта 3 в `app/blockchain/transaction.py`, `block.py`, `chain.py` и реализовал строгую валидацию входящих блоков (`validate_incoming_block`, `receive_block`).
  * Реализовал конфигурацию ноды (`app/core/config.py`) и Pydantic-схемы валидации контрактов (`app/schemas/node.py`).
  * Написал бизнес-логику сетевого узла (`app/services/node_service.py`): регистрацию и инспекцию пиров, рассылку (`broadcast_block`) и запрос блоков (`fetch_block_from_peer`) через асинхронный `httpx.AsyncClient`.
  * Реализовал эндпоинты (`app/api/v1/endpoints/nodes.py`), фабрику FastAPI-приложения с CORS (`app/main.py`), скрипт запуска независимых инстансов (`run_node.py`) и список зависимостей (`requirements.txt`).
* **Артефакты:** `app/blockchain/*`, `app/core/config.py`, `app/schemas/node.py`, `app/services/node_service.py`, `app/api/v1/*`, `app/main.py`, `run_node.py`, `requirements.txt`.

### 4. UI-разработчик / Дизайнер (Участник 4)
* **Зона ответственности:** проектирование пользовательских сценариев и реализация стартового веб-интерфейса ноды.
* **Что сделал:**
  * Спроектировал визуальный интерфейс панели управления нодой в тёмной теме с индикацией статуса целостности цепочки и удобным просмотром хешей.
  * Реализовал одностраничный Web UI (`app/static/index.html`) без необходимости отдельной сборки фронтенда — каждая нода отдаёт свой интерфейс прямо на `/`.
  * Реализовал ключевые виджеты: сводку состояния ноды (высота, пиры, `genesis_hash`, `last_block_hash`), форму создания блока с опцией мгновенной рассылки (Push), панель подключения/инспекции/запроса блоков (Pull) у пиров, интерактивный журнал сетевых ответов и обозреватель цепочки блоков.
  * Подготовил визуальную и техническую базу для расширения UI на следующем спринте (демо-спринт с акцентом на интерфейс).
* **Артефакты:** `app/static/index.html`, интеграция раздачи UI в `app/main.py`.

### 5. Тестировщик (Участник 5)
* **Зона ответственности:** разработка тест-плана, автоматизация интеграционных и негативных тестов, сквозная приёмка системы.
* **Что сделал:**
  * Сформировал набор из 13 тестовых сценариев (6 позитивных и 7 негативных), покрывающих все требования приёмки спринта.
  * Написал автоматизированный интеграционный тестовый модуль (`tests/test_network.py`) с кастомным `MultiNodeTransport`, поднимающим две независимые FastAPI-ноды с отдельными файлами хранилища и реальным обменом HTTP-запросами.
  * Автоматизировал проверку всех негативных кейсов: подмена данных транзакции, искажение хеша блока, неверный `prev_hash`, пропуск индекса, отправка дубликата, недоступность пира.
  * Провёл ручное сквозное тестирование запуска двух и более нод в разных терминалах, проверил работу Web UI, Swagger API и восстановление цепочки после перезапуска нод.
* **Артефакты:** `docs/sprint4-test-scenarios.md`, `tests/test_network.py`.

## 5. Задел на следующий спринт

Система полностью готова к следующему этапу:
1. На базе `app/static/index.html` и открытых REST-эндпоинтов можно развивать полноценный UI (фильтрация и трекинг конкретных отправлений `shipment_number`, загрузка и сверка хешей внешних документов, визуализация графа сети).
2. На базе `GET /api/v1/blocks` и `POST /api/v1/blocks/fetch` легко добавить автоматическую синхронизацию отстающих нод и разрешение конфликтов цепочек.
